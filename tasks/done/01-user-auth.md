# 📋 Task: 01-user-auth

## 1. Контекст / Зачем

В текущем состоянии приложение предоставляет общий список задач. Для полноценного использования необходимо разграничить данные между пользователями, чтобы каждый имел свой приватный список задач.

## 2. Цель

Реализовать систему регистрации, авторизации и управления профилем пользователя с полной изоляцией данных на уровне базы данных.

## 3. Acceptance criteria

- [ ] Пользователь может создать аккаунт (email, пароль).
- [ ] Пользователь может авторизоваться и выйти из системы.
- [ ] Неавторизованный пользователь при попытке зайти в приложение перенаправляется на страницу `/login`.
- [ ] После обновления страницы пользователь остается авторизован (сессия сохраняется).
- [ ] Пользователь видит и может редактировать **только свои** задачи.
- [ ] Реализован механизм сброса/восстановления пароля.
- [ ] Есть страница профиля для смены личных данных.

## 4. Затрагиваемые файлы

**Backend (`apps/backend/`):**

- Схема БД (создание таблицы `users`, обновление таблицы задач).
- Роуты аутентификации (регистрация, логин, выход, сброс пароля).
- Middleware для проверки JWT токена.
- Контроллеры задач (фильтрация по `user_id`).
- Контроллер профиля пользователя.

**Frontend (`apps/frontend/`):**

- `src/pages/LoginPage.vue`, `src/pages/RegisterPage.vue`, `src/pages/ProfilePage.vue`, `src/pages/ResetPasswordPage.vue`.
- `src/router/index.js` (Navigation Guards).
- `src/store/` (хранилище пользователя и токена).
- `src/api/` (обновление API-клиента для передачи токена).

## 4.1 Технические решения (приняты автоматически)

- **Безопасность паролей:** Использование `bcrypt` для хеширования паролей перед сохранением в БД.
- **Механизм сессий:** Использование JWT (JSON Web Token) для stateless авторизации.
- **Валидация:**
  - Применение `.trim()` ко всем строковым вводам.
  - Валидация email через регулярные выражения на фронте и бэке.
  - Проверка минимальной длины пароля.
- **UX/UI:**
  - Автофокус на первом поле ввода в формах.
  - Индикация загрузки (loading state) при отправке форм.
  - Понятные сообщения об ошибках (например, "Email уже занят" вместо "Internal Server Error").
- **Обработка ошибок:** Использование единого middleware для перехвата ошибок на бэкенде и возврата корректных HTTP-статусов (400, 401, 403, 404).
- **Политика пароля:** минимум 6 символов, одна заглавная буква, одна цифра (проверка на фронте и бэкенде).

## 5. План реализации

1. **Бэкенд: БД.** Создать таблицу `users` и добавить `user_id` в таблицу задач. Написать миграцию или скрипт обновления.
2. **Бэкенд: Auth.** Реализовать эндпоинты `/api/auth/register`, `/api/auth/login`, `/api/auth/logout`.
3. **Бэкенд: Middleware.** Создать слой проверки JWT токена для защиты эндпоинтов.
4. **Бэкенд: Данные.** Обновить CRUD задач, чтобы все запросы фильтровались по `user_id` из токена.
5. **Фронтенд: API & Store.** Настроить хранение токена в `localStorage` и автоматическую вставку `Authorization: Bearer <token>` в заголовки запросов.
6. **Фронтенд: Страницы Auth.** Создать страницы регистрации, входа и восстановления пароля.
7. **Фронтенд: Router.** Внедрить Navigation Guards для защиты приватных маршрутов.
8. **Фронтенд: Профиль.** Реализовать страницу редактирования профиля.

## 6. Риски / edge cases

- **Дубликаты:** Обработка попыток регистрации на существующий email.
- **Невалидные данные:** Ввод некорректных email или слишком коротких паролей.
- **Безопасность ID:** Защита от прямого обращения к чужой задаче через ID в URL/теле запроса (проверка владения на бэке).
- **Просроченный токен:** Обработка 401 ошибки на фронте $\rightarrow$ автоматический редирект на `/login`.

## 7. Как тестировать

**Локально:**

- Регистрация $\rightarrow$ Логин $\rightarrow$ Проверка токена в `localStorage`.
- Создание задач под разными пользователями $\rightarrow$ проверка отсутствия доступа к чужим данным.
- Попытка зайти на `/` без авторизации $\rightarrow$ проверка редиректа.
- Смена пароля $\rightarrow$ проверка невозможности войти по старому.
- Перезагрузка страницы $\rightarrow$ проверка сохранения сессии.
