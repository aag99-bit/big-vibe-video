# 🎯 Skill: Task Creator

## Как работает (главная суть):

1. **Читает AGENTS.md** — подтягивает стек, порты 3001/5173, эндпоинты API, схему БД, правило «Docker локально не запускать», деплой через deploy.sh.
2. **Ведёт интервью блоками по одному за сообщение** (Суть → Сценарии → Acceptance → Тех.детали → Edge cases → Тестирование). Переспрашивает в блоке, пока неясно, и только потом идёт дальше.
3. **Перед генерацией прогоняет чек-лист полноты** и резюмирует задачу — файл создаётся только после подтверждения пользователя.
4. **Автонумерует файлы** (01-...md, 02-...md ...) и пишет ТЗ по шаблону со всеми секциями.

## Активация:

- **Автоматически** — когда формулируешь задачу в свободной форме.
- **Явно** — командой `/skill:task-creator` (если в /settings включено enableSkillCommands).

## Процесс работы:

### Шаг 1: Чтение контекста

Перед началом работы ОБЯЗАТЕЛЬНО прочитай файл `agents.md` в корне проекта, чтобы узнать текущий стек, структуру, API и ограничения.

### Шаг 2: Интервью (блоки по одному)

Задавай вопросы блоками, по одному блоку за сообщение:

- **Блок 1: Суть задачи** (Что делаем? Какую проблему решаем?)
- **Блок 2: Сценарии использования** (Как пользователь будет это использовать?)
- **Блок 3: Acceptance criteria** (Как поймем, что задача выполнена?)
- **Блок 4: Технические детали** (Какие файлы изменить/создать?)
- **Блок 5: Edge cases** (Что может пойти не так?)
- **Блок 6: Тестирование**
  - Ручные проверки (curl-команды, что открыть в браузере)
  - Автоматические тесты (какие тесты написать в `apps/backend/tests/`)
  - Сценарии: успех + ошибка + граничный случай

### Шаг 3: Чек-лист полноты

Перед созданием файла проверь, что ТЗ содержит все 10 секций (включая 4.1 и 7.1):

- [ ] 1. Контекст / Зачем
- [ ] 2. Цель
- [ ] 3. Acceptance criteria
- [ ] 4. Затрагиваемые файлы
- [ ] 4.1 Технические решения (приняты автоматически)
- [ ] 5. План реализации
- [ ] 6. Риски / edge cases
- [ ] 7. Как тестировать (ручные проверки)
- [ ] 7.1 Сценарии автотестирования (jest/supertest)
- [ ] 8. Ограничения проекта

### Шаг 4: Создание файла

После подтверждения пользователя:

1. Найди следующий свободный номер в папке `tasks/` (01, 02, 03...)
2. Создай файл `tasks/NN-краткое-название.md`
3. Заполни ТЗ по шаблону из `.pi/skills/task-creator/references/task-template.md`
4. Напиши в чат: "✅ ТЗ сохранено в `tasks/NN-название.md`. Жду команды 'Выполняй' для начала работы."

После команды "Выполняй" активируется скилл **task-solver**, который реализует задачу по плану из ТЗ и переместит файл в `tasks/done/`.

## ⚠️ ВАЖНОЕ ПРАВИЛО: Проактивные технические решения

При создании ТЗ ты ОБЯЗАН самостоятельно дополнять раздел "4.1 Технические решения (приняты автоматически)".
**НЕ спрашивай** пользователя о валидации, обработке ошибок или UX-деталях. Просто примени лучшие практики (best practices, например: `.trim()`, `try/catch`, автофокус) и опиши их в разделе 4.1, чтобы пользователь видел профессиональный подход и учился на этом.

---

## ⚠️ ВАЖНОЕ ПРАВИЛО: Автоматические тесты

При создании ТЗ ты ОБЯЗАН добавить секцию **"7.1 Сценарии автотестирования"** со списком тестов для `apps/backend/tests/`.

**Принцип:**
- Каждый новый эндпоинт API = минимум 2 теста (успех + ошибка)
- Каждое изменение бизнес-логики = тест на граничный случай
- Тесты должны быть изолированными (создают своего пользователя через `/api/auth/register`)
- Пароль для тестов: `Password1` (соответствует политике проекта)

**Пример секции 7.1 в ТЗ:**

    ## 7.1 Сценарии автотестирования
    Файл: apps/backend/tests/feature-name.test.js

    Тесты успеха:
    - [ ] Создание ресурса с валидными данными → 201
    - [ ] Получение списка ресурсов → 200

    Тесты ошибок:
    - [ ] Создание без токена → 401
    - [ ] Создание с невалидными данными → 400
    - [ ] Доступ к чужому ресурсу → 404

    Edge cases:
    - [ ] Пустой список → возвращает []
    - [ ] Дубликат уникального поля → 400
